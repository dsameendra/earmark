## Scope and completion policy

Implement the proposed speech and translation model families below through working, native, offline inference integrations. Downloads, descriptors, mocks and upstream demos do not establish model support. Complete each model's applicable product workflows and verify actual downloaded checkpoints. No silent deletion or deferral of a proposed family: if native feasibility, licensing, hardware or quality blocks completion, record the evidence and obtain an explicit scope decision before treating 1.1.0 as ready. No promise that every model supports every language or feature.

The plan covers local Apple-silicon macOS 26+ operation. Keep Swift 6 concurrency, both supported toolchains, user-initiated model downloads, separate weights, no telemetry and no release Python dependency. Preserve existing Apple/Whisper/Sinhala paths while new engines are integrated. Use small, reviewable commits and checkpoint PRs rather than one final integration dump. Do not publish or move release tags during implementation.

## Models page, additional catalog and supported imports

Owner refinement: keep the Models page compact while providing properly integrated access to the broader range. Curated catalog installation and user imports share the same verified acquisition/lifecycle pipeline. Import support is deliberately narrower than the full implemented model catalog: only documented import profiles with a tested architecture, tokenizer, configuration and native adapter are accepted.

### Compact primary page

- Present a small Recommended area (target 4–6 suggestions across current speech/translation needs), chosen by selected languages, use case, measured hardware suitability and license eligibility. Avoid a card for every size, quantization or translation direction. If evidence is insufficient, say so rather than inventing speed/memory recommendations.
- Keep Installed models as a compact searchable list with active-use indicators, storage and update/validation state. Existing custom WhisperKit models remain visible and usable where compatible. Place larger catalogs behind Add models…; expose Import model… from that flow and as an accessible secondary action.
- Never silently replace a user's selected model when recommendations change. No automatic model download merely from visiting a tab or changing language. Loading/system-asset readiness must not masquerade as a missing downloadable model.

### Add models flow

- Open a searchable, filterable sheet/window with Speech recognition, Translation and Speaker support categories. Show suggested models first; offer Browse all for the full supported catalog and a separate Import from Hugging Face / Import local folder route. Group checkpoint sizes/quantizations under families and open details on demand.
- Filter by spoken language, translation source/target direction, file/live/dictation/meetings use, speaker/overlap capabilities, download size, hardware fit and license. Show relevant limitations in plain language. Search operates on supported catalog records; a Hugging Face link is not universal remote model search or implied compatibility.
- Translation pair packs use source/target selectors and explicit direction labels. One direction is not bidirectional unless both artifacts really support it. Offer both directions when available, list direct vs pivot requirements, and show combined download size and licenses before adding multiple packs. Group installed pairs under their family; do not fill the main page with individual pair cards.
- Details show exact model/conversion identity, supported tasks/languages/directions, revision, download size, hardware evidence and validation state. Distinguish a disabled unsupported task from an installable missing dependency. System Apple packs keep their dedicated system installation flow.
- Every catalog choice must reach a functioning engine, model picker and applicable workflows. A runtime not shipped in this app cannot be installed by downloading weights and must not appear as an actionable model choice.

### Import profiles and scope

- Define versioned import profiles per supported adapter, with exact accepted config schemas, tensor names/shapes, tokenizer/preprocessor files, quantizations, language/direction metadata and required dependencies. Start from profiles proven against the curated checkpoints in M0. Accept local folders and supported Hugging Face repository/file URLs only through these profiles.
- Preserve the existing WhisperKit Core ML folder workflow; move its checks behind the shared importer without changing valid existing imports. Add a selected set of Qwen MLX, translation native-format and pair-pack profiles only after their real adapter conformance tests pass. Other families can remain curated-only until their import profiles are independently proven; list that distinction explicitly in the support matrix.
- Support a finite, published set of tested source recipes/checkpoints per profile initially. Matching an extension, a model_type string or an architecture family name is insufficient. Unlisted fine-tunes/conversions are accepted only where the profile explicitly allows them and all compatibility gates pass; otherwise return an actionable unsupported-model explanation. Never fabricate an adapter, language capability or tokenizer to accept a repository.
- User-supplied names may rename a model for display; they cannot override detected architecture, supported tasks, languages, translation directions or license. Imports must not claim upstream language/quality coverage based on a manual checkbox or untrusted README alone.

### Inspect, acquire, validate and activate

1. Inspect the user-selected URL/folder and a bounded set of metadata; identify a supported profile or explain the incompatibility before large downloads. Normalize Hugging Face URLs and validate redirects/download hosts under the existing network policy. Resolve a selected branch/tag to an immutable commit and pin the entire manifest to that commit; never mix revisions as a download resumes.
2. Preview recognized identity, tasks/languages, dependencies, exact revision and size, available disk/resource limits and license requirements. Downloads start only after the user's Add/Download action. Public repositories are the initial default; private/gated repositories either use an explicitly supported credential flow or produce a clear access explanation. Never accept license terms automatically or persist tokens in model manifests/logs.
3. Stage acquisition outside active models, with bounded downloads, progress, cancel/resume, disk-space checks and manifest/hash verification. Download required data artifacts only; do not execute repository Python, trust_remote_code, install scripts or arbitrary custom tokenizer code. Do not replace the bundled runtime. Validate local copies for missing/truncated files, symlink escapes and format/shape/config mismatches.
4. Compile/load with the actual native adapter in a bounded validation session (isolated worker where available), with timeout/cancellation and cleanup. Run small built-in non-private inference fixtures for each advertised task and representative supported language directions; test every direction of an imported pair pack. Check valid output/schema and basic language/task behavior. A successful load alone is insufficient. Imports cannot start microphone capture or use library transcripts for this test without a separate user action.
5. Commit the model atomically only after acceptance; register it using the shared catalog/compatibility/router path. Failed/cancelled imports must not become installed or overwrite an existing working model. Preserve stable IDs/provenance across restarts and support deliberate revalidation/replacement when the runtime/profile changes.
6. Show precise status: Curated and tested (exact reviewed artifact), Compatible import (structural and smoke checks passed; quality not independently benchmarked), Validating, or Failed with a recovery action. Do not present imported weights as trusted/quality-verified merely because inference succeeds. Ordinary user UI should use understandable labels and put backend details in model details/diagnostics.

### Shared lifecycle and acceptance

- Imported and curated models share selection, language routing, readiness, storage, pause/resume/cancel, removal, license eligibility and resource coordination. Shared tokenizers/dependencies are reference-counted or otherwise protected from deleting a resource used by another model.
- Existing persisted custom imports remain supported through explicit legacy migration/revalidation rules, without surprise redownloads or silently disabling a working selected model. If an incompatibility is detected, retain the record and explain recovery; never erase its files automatically.
- Test supported and rejected profiles; incorrect tokenizer/config/architecture/quantization; corrupted/incomplete weights; wrong translation direction; changing remote revisions; interrupted/cancelled imports; duplicate imports; offline restart; private/gated access errors; invalid URLs/host redirects; shared dependency deletion; migration and packaged-runtime validation.
- UI tests cover the compact page, Browse all filters, family variant details, source/target pair selection, both-direction installation, local-folder/Hugging Face import, validation errors and successful model selection. Test keyboard/VoiceOver and compact windows. Real-model tests prove at least one accepted import for every advertised profile and representative rejection cases; full curated-checkpoint QA remains a separate gate.

## Implementation sequence and gates

### M0 — Establish baseline and exact support matrix

1. Preserve source baseline, installed app versions, dependency locks and existing release artifacts. Run serial package suites, static checks and full UI suite; record skips separately.
2. Capture representative real-service behavior before edits: file jobs, microphone/system audio, Live, dictation, meetings, editor playback, translation and exports. Use test libraries and settings backups; never mutate the owner's library for benchmarks.
3. Create exact model/checkpoint registry with authoritative source links and runtime compatibility. Include supported source/target languages, scripts, automatic ID, code-switching, word timing, speaker counts, live/file operations and measured vs unmeasured status.
4. Run bounded feasibility spikes for every new architecture before scheduling product integration. Python/reference tooling may be used only in isolated development environments. Compare native outputs on the same fixtures. No public runtime downloads at app launch.
5. Define the initial curated catalog and separately enumerated import profiles/checkpoints, wireframes for Recommended / Installed / Add models, pair-pack grouping and acceptance fixtures.
6. Approve concrete AppCore additions through SCR-016 before editing contracts. Freeze benchmark data, scoring rules and pass/fail thresholds before comparing candidates.

Exit: baseline evidence, exact artifact register, backend decisions and explicit blockers. Do not infer Mac performance from CUDA benchmarks or parameter count.

### M1 — Contracts, compatibility and persisted-state migration

- Extend capability representation only as needed: language/direction/task coverage, native vs buffered streaming, actual engine availability, model readiness, speaker-attributed ASR and overlap. Avoid embedding vendor types in AppCore.
- Existing `PartialSegment` has no speaker identity and existing Live storage is not proven to retain simultaneous partials. Add stable stream/speaker identity and revision/finalization semantics where necessary; audit all consumers and adapters.
- Preserve existing Codable payloads with conservative defaults. Test old settings, presets, models/state.json, queued jobs, transcripts and missing-media records. Back up migration fixtures and test interrupted migrations.
- Define import-profile validation results, immutable source provenance, compatible-vs-curated status and atomic installation lifecycle through SCR-016; preserve existing custom IDs and dependency ownership.
- Introduce centralized resource ownership for GPU/MLX/Core ML/native workers: avoid unloading an engine used by another task; bounded concurrency and memory, explicit switching, cancellation and crash recovery.

Exit: contract tests and old-data compatibility pass; existing engines remain behaviorally intact.

### M2 — Fix user-facing routing and translation behavior

- Refresh Apple Speech readiness for the actual selected language before routing; no unchecked readiness assumption. Explain missing assets and offer explicit install/fallback without an unrequested download.
- Make the translation engine preference reach execution and readiness checks. Respect explicit model choice, language pair and license eligibility consistently across editor, jobs, Live and dictation.
- Add independent Translate captions control, source/target selectors, active engine and availability messages to Live. Translation behavior must not depend on appearance presets. Migrate preset-based behavior predictably, preserving user styling and existing choices.
- Provide translation progress/lag, actionable failure states and retry. Retain the original caption on translation failure. Define whether a settings change applies immediately or requires restart; display that behavior accurately.
- Implement the compact Models page, supported-catalog browser, family variant details, directional pair-pack flow and shared validated local/Hugging Face importer described above. Build the UI and shared intake here; enable each model-specific profile only after its M3–M5 engine acceptance, never through a placeholder.
- Use DesignSystem controls, accessibility identifiers and keyboard/VoiceOver support; test RTL and non-Latin shaping.

Exit: reproduce the reported missing-Apple-assets and no-translations cases; both have automated regression tests and real-service verification.

### M3 — Native recognition integrations

Integrate ASR-01 through ASR-08 in dependency order: existing Whisper/Qwen first; shared Core ML speech adapter next; dedicated streaming and larger native engines after their feasibility gates. Update checkpoints separately with per-family tests. Maintain separate speaker diarization for engines lacking intrinsic speaker output. Never invent unsupported features to fit the interface.

For each engine verify all applicable entry points: file queue, progressive transcript, pause/resume/checkpoint recovery, cancellation, re-transcribe, live mic/system/mixed capture, meetings and dictation. Recognition APIs must never silently translate the source speech.

Exit: real-model conformance report per selected checkpoint; only passing operations are enabled in routing and pickers.

### M4 — Native translation integrations

Integrate TR-01 through TR-06, reusing native infrastructure where architectures really match. Implement direction-aware routing, direct vs pivoted paths and explicit engine selection. Audit references, tokenizers and conversion parity rather than trusting filenames or generic format labels.

For generative translators bound context/output, prevent explanations or prompt echo, treat transcript text as data, and test names, numbers, negation, punctuation and scripts. Keep live work queues bounded: coalesce obsolete partials, prioritize finals, cancel stale jobs and surface sustained lag. Do not silently lose final translations at stop/restart.

Exit: actual file/editor/live translation tests for supported tasks; model readiness and license decisions match execution. No selectable descriptor without a functioning runtime.

### M5 — Speaker-attributed overlapping recognition

Implement ASR-09 with independent speaker streams and stable IDs. Validate both speakers' words during simultaneous speech, interrupted turns, diarization mistakes and changing speaker count. Prevent double labeling when an engine supplies its own speaker attribution.

Audit persistence, editor ordering, selection, highlights, translation and playback for overlapping time ranges. Preserve both speakers in exports; use appropriate ordering/track options and explain subtitle-format constraints. Compare against existing ASR + diarization using overlap-aware WER and speaker-attributed error, not ordinary WER alone.

Exit: two-speaker and measured higher-speaker-count recordings pass on declared hardware with sustained ASR + diarization + translation. Conversion existence is not acceptance.

### M6 — Regression, performance and model acceptance

- Acquisition/UI acceptance: exercise every advertised import profile against real artifacts and negative fixtures; verify recommendation counts/grouping, catalog filters, pair directions, provenance, atomic registration, migrations and full installed-model lifecycle. No untested import profile may be advertised in the release.
- Automated: serial package suites; adapter/contract tests; migration fixtures; download corruption/resume/partial cleanup; unavailable-language/model paths; queue checkpointing; translation routing and bounded queues; worker failure/restart; speaker identity and overlap persistence; full UI suite.
- Real models: explicitly run tests skipped in CI. Record exact artifact hashes, OS/toolchain/hardware, cold/warm startup, memory, accuracy and skipped features. Compare quantized/native outputs with reference; do not require exact text equality where decoding is nondeterministic without a defined tolerance.
- Quality sample matrix: English, Sinhala, Tamil, Hindi, Bengali, Urdu, Spanish, French, German, Arabic, Mandarin, Japanese and Korean; per-model applicable subsets. Test both translation directions, non-English pairs, code-switching, script variants, names/numbers, noise and silence. Use licensed public fixtures plus consented examples. Document all supported-but-unreviewed languages separately.
- Hardware: start on the M3 Pro/18 GB Mac; gather physical 8 GB and larger-memory evidence before making recommendations for those tiers. Missing hardware is an explicit verification gap, never a fabricated benchmark.
- Sustained sessions: mic, system audio and mixed audio; recording enabled/disabled; multiple speakers; concurrent ASR/translation/diarization; background file job; model switch, memory pressure, device loss, sleep/wake and app restart. Live processing must keep up with incoming audio on the declared tier, with bounded backlog/memory. Publish measured latency distributions and thresholds per mode.
- Existing behavior: library edits/search, export formats, translations, non-destructive re-runs, meetings policy labels, no-recording vs missing recording, sidebar/Settings reopening, model selection, permissions and accessibility.
- Compatibility: local Xcode 27 plus Xcode 26.x/Swift 6.3 builds and all applicable tests; strict concurrency and zero warnings. Check dependency upgrades against both SDKs and existing helper/diarization behavior.

Exit: every model row has an implemented/verified outcome or an explicitly approved scope decision. A failing model blocks its acceptance; it is not relabeled supported because mocks pass. No claim of zero regressions solely from unit tests.

### M7 — Review, release candidate and distribution

1. Review contract, migration, runtime, license and UX changes; update notices, docs, website capability tables and reproducible build provenance. Review native dependency hashes and runtime packaging allowlists. Keep model weights external.
2. Set marketing version to 1.1.0; use the next unused monotonic build number above 2, incrementing for replacement update candidates. Retain the signing identity and Sparkle update key. Never overwrite a published build's bytes.
3. Open/review the feature PR; require static checks and successful macOS build/tests for this release even while hosted macOS remains informational in repository settings. Resolve failures and recorded flakes; do not change repository protections without separate authorization.
4. Build the exact committed signed release candidate. Validate bundled workers, arm64 architecture, deployment target, dynamic libraries, licenses, executable modes, symlinks, no secret/model/dev payloads, strict signatures and mounted DMG bytes/layout. Verify a clean metadata-free mounted copy as documented.
5. Test first install plus actual Sparkle 1.0.1→1.1.0 and 1.0.0→1.1.0 download/install/relaunch with the exact DMG. Verify library/settings/model preservation and the same certificate/update public key. Isolate update tests; remove temporary HTTPS trust and stop servers afterward.
6. Smoke the actual signed release with real microphone captions and translation, system audio, meetings and each new packaged engine. Validate real local-folder and Hugging Face imports through every shipped profile and a directional translation-pack install in the packaged app, including offline relaunch and selection. Mock UI results alone cannot satisfy this gate. Compare source builds and packaged helpers for parity.
7. Merge only after release acceptance. Any source change after the tested candidate requires a new candidate and affected checks. Tag the exact artifact source commit; record the distinction if later documentation-only commits exist.
8. Prepare reviewable release notes and draft assets; obtain final publication approval unless explicitly authorized at that stage. Publish normal latest release `Earmark 1.1.0`, tag `v1.1.0`, canonical DMG/checksum and appcast retaining previous entries.
9. Download public assets independently; check bytes/signatures/checksum/version/names, production latest feed and update availability. Require published-release verification success; keep 1.0.1 assets intact. Remediation uses a newer build/release or an approved feed correction, never tag movement or replacing signed public bytes.

Exit: evidence-backed release report identifies passed automated, actual-model, hardware, signed-artifact and public-update checks separately, and lists any explicitly accepted limits.
