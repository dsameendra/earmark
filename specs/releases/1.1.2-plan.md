## Scope

1. Fix the flaky hosted-CI Dictation tests first (they failed the 1.1.1 `build-and-test (macOS)` job twice).
2. Discord support.
3. Google Meet (and other browser call) support, no Google account involved.
4. Two manual controls on the Meetings page and in the menu bar that work for every meeting app: **Detect now** and **Record a browser call**.

## Goal

Meetings detects, prompts for, records and transcribes Google Meet and Discord calls the same way it does Zoom and Teams: detection, per-app behaviour (do nothing, ask first, transcribe, transcribe and record), "You" and remote tracks, finalisation, Library entry. Still 100% local, no new network use.

## How Zoom and Teams work today (what we reuse)

- `MeetingApp` (AppCore, `zoom | teams`) and `MeetingAppSignature.defaults` map an app to bundle-ID prefixes, executable names and optional call-only helper processes.
- `CoreAudioMeetingProbe` reads, per app, whether any of its audio processes has an input stream (microphone) and an output stream running. No polling, no permission.
- `ProbeMeetingDetector` debounces that signal into `started` and `ended` events (input and output 3 s; output plus corroboration 5 s; output only 15 s; end grace per app).
- `SystemMeetingSources.remoteSource` taps the app's audio by bundle ID. The tap matches the bundle ID and every `<bundle>.` helper, so Electron and Chromium helper processes are covered.
- Opt-in video records the app's largest window through ScreenCaptureKit, chosen by the same signature.

Discord fits this model directly. Google Meet does not, because it is a tab in a browser.

## Discord (native app): low risk

Discord is an Electron app (`com.hnc.Discord`, helpers `com.hnc.Discord.helper*`; Canary and PTB use sibling IDs). Its voice and video calls open a microphone stream and play remote audio from the app's own audio process, exactly the Zoom signal.

Work:
- Add `MeetingApp.discord`, a signature with prefix `com.hnc.Discord` (covers helpers) plus `executableNames: ["Discord"]`, and `bundleID(for:)` resolution for Canary and PTB.
- Detector tuning: Discord voice channels are long-lived and often idle, and bots play music into them. Defaults: behaviour `askFirst`, start only when microphone input is running (the output-only 15 s path is disabled for Discord so a music bot cannot trigger a prompt), end grace 30 s.
- Window recording: pick the Discord window, same code path as Zoom.

Open facts to verify on a real call in Phase 0 (not guessable): whether the microphone stream stays open while muted or push-to-talk, whether Discord keeps it open after leaving a channel, and which bundle IDs Core Audio reports. Settings, Meetings, Detection diagnostics already lists the active audio processes, so this needs no new tooling.

## Google Meet (browser): the design decision

A browser's audio process cannot tell a Meet tab from any other web call, so audio alone cannot identify Meet. Options considered:

| Option | Accuracy | Permission | Browsers | Verdict |
|---|---|---|---|---|
| Audio only (browser mic stream running) | Low: Zoom web, WhatsApp Web, Slack huddles, dictation sites all match | none | all | Too many false prompts |
| AppleScript tab URL | High, exact meeting URL | Automation, one prompt per browser | Chromium family, Safari; not Firefox | Many prompts, Firefox unsupported |
| Accessibility window title | Good: a Meet tab's window is titled "Meet - abc-defg-hij" | Accessibility (Earmark already asks for it for Dictation) | All, including Firefox | Recommended |
| ScreenCaptureKit window titles | Good | Screen Recording | All | Heavier permission than needed |
| Manual "Record this browser call" | Exact, user chosen | none | all | Required as the fallback, useful anyway |

Recommendation: **audio signal AND Meet window title, plus a manual start.**

Detection:
1. Probe a new signature group "browsers": Chrome (`com.google.Chrome`, which also covers installed Meet web apps), Edge, Brave, Arc, Vivaldi, Opera, Firefox. A browser counts as in a call when one of its audio processes has an input stream running (WebRTC opens the microphone) and output running.
2. A new injectable `MeetingContextChecking` seam reads that browser's window titles through the Accessibility API and returns true when one is a Meet call (title begins "Meet - " followed by a meeting code, or the "Meet" prefix with the camera/mic suffix). Fakes in tests, real implementation in `App/`.
3. Only then does the detector emit `started(.meet)`. When the title match is lost but audio continues, the meeting continues (a user switching tabs must not end it); the existing end grace applies.
4. The probe also reports which browser matched, so the remote tap targets that browser (new `captureTarget(for:)` on the probe; `SystemMeetingSources.bundleID(for:)` uses it instead of guessing).

Manual fallback: Meetings gets "Record a browser call" (also in the menu bar) that lists browsers currently using the microphone and starts a Meet-labelled session on the chosen one. This covers Safari, background tabs, no Accessibility permission, and any other web call service. Sessions started manually are labelled "Browser call".

Known limits to disclose in the UI and docs:
- The per-app tap captures all audio from that browser, including other tabs. The "You" track is the microphone only and stays clean. A one-line note in the consent notice and in the recording prompt: "Audio from other tabs in this browser is included."
- Safari plays web audio through shared WebKit processes (`com.apple.WebKit.*`), not a Safari-owned one. Safari is manual-start only in 1.1.2 until verified (Phase 0). Decision for the owner below.
- Without Accessibility permission, Meet is manual-start only. Discord and the other apps are unaffected.

### No Google account, no login (owner requirement)

Nothing in this design touches Google. There is no sign-in, no OAuth, no Calendar or Meet API, no browser extension and no reading of page contents or cookies. Detection uses only what the Mac itself exposes about the browser: which of its audio processes has the microphone open, and the title of its windows. Any Meet call in any signed-in or signed-out profile, guest join or Workspace account, looks the same to Earmark. It is not bound to an account, and Earmark never learns which account is in use.

### What is solid and what is unproven (checked against the code and platform behaviour, not against a live call)

| Claim | Status |
|---|---|
| Core Audio lists per-process input/output state for any app, including browser helper processes, with no permission | Solid: Zoom and Teams detection already rely on it in production |
| The audio tap matches a bundle ID and all its `.`-prefixed helpers, so Chrome's helper processes are captured | Solid: `HAL.processObjects(bundleID:)` does this today |
| Reading window titles through Accessibility works for any browser, no login, no per-browser prompt | Solid in principle: it is a standard API, and Earmark already holds the Accessibility permission for Dictation |
| Chrome, Edge, Brave, Arc, Firefox put the active tab's title in the window title | Very likely; confirm in Phase 0 |
| A Meet call tab is titled "Meet - abc-defg-hij" | Believed, not confirmed. The lobby and in-call titles may differ, so Phase 0 records both and the matcher accepts either |
| Only the active tab's title is visible, so a call in a background tab is not seen by title | True limit. Mitigation: once a call has started it keeps going while audio continues, and the manual start covers a call that was in a background tab from the beginning |
| Firefox exposes the microphone stream under its own audio process | Likely, unproven |
| Safari: web audio is played by shared WebKit processes, not by Safari, so the "browser using the microphone" signal may not map to Safari | Unproven and the weakest link. Phase 0 decides whether Safari is detected automatically or manual-start only |

So the user's goal, "notice that a Meet call is going on in Chrome, Safari or Firefox", is plausible for Chrome and the Chromium family with high confidence, likely for Firefox, and uncertain for Safari. The plan does not promise Safari auto-detection; it promises to test it first and to ship the manual start for it either way. Anything the detector cannot see automatically is never silently skipped: it is reported in Detection diagnostics and covered by "Record a browser call".

### Detect meetings (one button, live list), replaces the separate Detect now and Record a browser call controls

Single button **Detect meetings** (Meetings page toolbar and empty state, menu bar). It rescans immediately and the Meetings page shows an **Available now** section that lists every live call Earmark can see, updated live (Zoom, Teams, Discord, Meet in a browser, and any other browser that has the microphone open, labelled Browser call). Each row has a **Transcribe** action (ask-first rules do not apply: an explicit tap starts it). A browser that is using the microphone but is not recognised as Meet is listed as a Browser call so it can still be recorded. Everything below describes the scan behaviour; read "Record a browser call" as the Browser call rows in this list.

### Detect now: a manual re-check for every meeting type

Problem: detection can be missed. The notification may have been dismissed or never seen, Focus mode may have hidden it, the behaviour may have been "Do nothing" for that app, or the user may have said no to an earlier prompt. Today there is no way to ask Earmark to look again.

Add a **Detect now** button, next to **Record a browser call**, on the Meetings page (toolbar and empty state) and in the menu bar menu. It works for all four apps (Zoom, Teams, Meet, Discord) and any browser Earmark knows.

Behaviour:
1. One scan, immediately, without the debounce timers (the user is telling us a call is happening). The detector gets `detectNow()`, which reads the probe once per app and applies a relaxed rule: audio output running together with microphone input, the call helper, or a Meet title; or microphone input alone for an app whose signature allows it. Same signature tables, so nothing new to maintain.
2. Found one call: show the normal "Record this meeting?" prompt for it, even if that app's behaviour is "Do nothing" or the user declined earlier (an explicit tap is consent to be asked). Choosing it starts a session exactly like an automatic start, so the transcript, tracks, finalisation and Library entry are identical.
3. Found several (Zoom and a Meet tab): a small list to pick from.
4. Already recording that meeting: say so and offer Stop, never start a second session.
5. Found nothing: a popover that says what was checked and what was seen ("Zoom: not running. Chrome: microphone not in use. Discord: running, no call audio"), with a link to **Record a browser call** and to Settings, Meetings, Detection diagnostics. It never fails silently.
6. Permissions: if Accessibility is missing the result says Meet could not be checked and offers the grant. Everything else works without it.

Also: Detect now reuses the diagnostics already in Settings, Meetings, so support requests can say what the app saw.

## CI fixes (do first, about half a day)

Hosted `build-and-test (macOS)` failed on the 1.1.1 pull request. Two different tests in the Dictation package failed in different runs, with the same root cause:

- `releaseDuringAccessibilityCheckDoesNotLeaveDictationListening` (first run: `ControllerTests.swift:112`, `:115`, `:118`)
- `cancelDuringAccessibilityCheckIsHonoured` (second run: `ControllerTests.swift:128`, `Expectation failed: !(h.hud.log.contains { $0.hasPrefix("show") })`)

The first passed on a rerun and both pass on the local machine, and no Dictation code changed in 1.1.1, so these are test races, not product bugs.

Cause: both tests use sleeps as synchronisation. `FakePermissions(delay: 200 ms)` makes the Accessibility check take 200 ms; the test sleeps 50 ms and then sends "released" or "cancel", expecting the press to be inside the check at that moment. On a busy hosted runner `Task.sleep` can overshoot, so the 200 ms check may already be over (the HUD has shown and the expectation fails), or the press task may not have started the check yet.

Fix (test code only, `Packages/Dictation/Tests/DictationTests/Fakes.swift` and `ControllerTests.swift`):
1. Replace the timed `delay` with a gate. `FakePermissions(holdAccessibilityCheck: true)` makes `status(.accessibility)` signal "check started" and then wait until the test calls `releaseCheck()`.
2. In both tests, wait for the "check started" signal (not 50 ms), send `released` or `cancel`, then open the gate. The order is guaranteed instead of timed, so the race disappears.
3. Replace other timing-based waits in `ControllerTests` where a signal exists; keep `eventually {}` only for output that genuinely arrives later.
4. Stress check: run the two tests about 200 times in a loop locally under CPU load before and after the fix, and record both results in the QA log.

Note on the pasted log: the job stopped at Dictation, so the packages after it (Features, Jobs, the speech packages and others) were not exercised in that run. After the fix the whole `scripts/check.sh unit` run must pass end to end. Also sweep the test folders (with `git grep`) for the same shape, a `Task.sleep` followed by an expectation about intermediate state, list them in the QA log, and fix any that depend on timing.

Gate: `scripts/check.sh unit` green on the hosted runner three times in a row (rerun the job twice on the pull request) before the feature work merges.

## Phases and gates

**Phase A: CI fixes (about half a day).** Described above. Merge first.

**Phase 0: verify on real calls (about 1 day, go/no-go).** On this Mac, with Settings, Meetings, Detection diagnostics open, record the audio processes and flags for: Discord voice channel (unmuted, muted, push to talk, after leaving), Meet in Chrome, Arc, Firefox, Safari (mic on and off, tab in background), and the Meet window title for each. Gate: Discord produces a clean input and output signal; Chrome-family and Firefox expose a readable Meet title through Accessibility. Failures are recorded and trigger a scope decision, not a silent drop.

**Phase 1: Discord (1 to 2 days).** Contract change, signature, tuning, window recording, tests, a real-call check. Shippable on its own.

**Phase 2: Meet detection (2 to 3 days).** Browser signatures, `MeetingContextChecking` with a fake and the Accessibility implementation, probe `captureTarget`, detector rules, tests (tab switch does not end a call, a non-Meet web call does not start one, two browsers, Meet in an installed web app).

**Phase 3: UI and manual controls (2 to 3 days).** Detection menu, "Record a browser call", "Detect now" (detector `detectNow()`, result popover, menu bar entry, tests for found, several, already recording and nothing found), Settings, consent and permission copy, VoiceOver and keyboard pass.

**Phase 4: QA and release (1 day).** Unit tests per package with `--no-parallel`, the UI suite, a real call for each app and browser group, the update path from 1.1.1 on a local HTTPS feed, release per `CLAUDE.md`.

Estimate: 7 to 10 working days.

## Risks

| Risk | Mitigation |
|---|---|
| Discord keeps its microphone stream open outside calls | Phase 0 measures it; ask-first default; longer end grace; fall back to the corroborated path |
| Meet title format changes | Match loosely on the meeting-code pattern; manual start always works |
| Other tab audio in the browser tap | Disclosed; mic track clean; per-tab isolation is not possible with Core Audio taps |
| Safari audio is not owned by Safari | Manual start only until verified |
| Accessibility permission friction | Optional; only Meet auto-detect needs it; manual start needs nothing |
| Flaky tests hide real failures in CI | Phase A removes timing-based synchronisation and requires three green hosted runs |
| Detect now starts a recording the user did not want | It only ever shows the prompt; nothing records until the user confirms |
| Consent for recording other people | Existing consent notice extended to name both apps |
