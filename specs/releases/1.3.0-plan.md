# Earmark 1.3.0: overlapping-speech recognition (Multitalker Parakeet)

Status: proposed, not started. Owner approval of this plan is required before implementation.
Branch (when approved): `feature/1.3.0-multitalker-asr`.
Baseline: `main` after the 1.2.2 release (`v1.2.2`, `Earmark-1.2.2.dmg`).
Release identity: Earmark 1.3.0, tag `v1.3.0`, `Earmark-1.3.0.dmg`, checksum and appcast per the rules in `CLAUDE.md`.
Related: [1.1.0 plan](1.1.0-plan.md) row ASR-09, [SCR-016](../changes/SCR-016-multilingual-models-and-overlapping-speech.md), [QA log](../qa/1.1.0-progress.md).

## Goal

When two or more people talk at the same time, Earmark transcribes each person's words as a separate, correctly attributed stream, live and from files, entirely on device. Today overlapping speech comes out as one merged stream from the normal engine, with speakers labelled afterwards by diarization.

Model: `nvidia/multitalker-parakeet-streaming-0.6b-v1` (English, streaming, cache-aware, speaker-kernel conditioned, up to 4 speakers). It needs speaker activity from Sortformer as an input, so overlap recognition is a pairing of the two models, not a standalone ASR engine.

## Why it was not in 1.1.0 (evidence to build on)

- Upstream transcribe.cpp 0.4.x cannot run the model as designed: `src/arch/parakeet/model.cpp` states that `diarize=ON` is unsupported on the streaming API and decodes a single speaker. The Earmark worker refuses that combination and reports `canStreamWithSpeakers=false`.
- On two frozen two-voice mixtures, Q4 and F16 recovered one speaker and scored 53.85% to 59.62% cpWER against a floor of 25% (`specs/research/1.1.0-speech-worker-evidence.json`, `1.1.0-fleurs-overlap-evidence.json`).
- The model card's weights (`.nemo`, 2.49 GB) and two converted forms exist: GGUF (`handy-computer/...-gguf`) and MLX (`animaslabs/...-mlx`). Neither has been shown to apply the speaker kernels.
- Contracts are already in place from SCR-016: `ModelCapabilities.overlapRecognitionSpeakers`, native one-based speaker ids in worker snapshots, retained overlapping intervals. Missing: per-speaker partial identity in `AppCore`, and the app-side pairing with Sortformer.

The failure is a missing mechanism (speaker conditioning), not weak weights, so the first phase proves the mechanism before any product work.

## Non-negotiables

Local only, no telemetry, Swift 6 strict concurrency on Xcode 26 and 27, `AppCore` contract changes through a numbered change request (SCR-017, next free number), DesignSystem tokens, accessibility identifiers on every control, Reduce Motion/Transparency/Contrast intact, no release Python dependency, downloads only when the user starts them, separate weights, existing engines unchanged. No silent deferral: if a gate fails, record the evidence and get an explicit scope decision.

## Phase 0: mechanism feasibility (go/no-go, about 1 week)

Question: can we run the real speaker-conditioned graph on Apple silicon at real-time speed?

Candidate backends, evaluated in this order, stop at the first that passes:

| Option | What it is | Main risk |
|---|---|---|
| A. Core ML via FluidAudio-style conversion | Convert the NeMo encoder with speaker-kernel injection, decoder and joint to Core ML; reuse the Parakeet adapter pattern and the app's existing Sortformer stack | Cache-aware streaming state and the per-speaker kernel injection must survive conversion; ANE compile time |
| B. Extend transcribe.cpp (ggml/Metal) | Implement kernel injection and per-speaker decoder state in the pinned fork behind the existing worker | Upstream divergence; maintenance of a fork; need to prove parity with NeMo |
| C. MLX port (`animaslabs` weights) | Swift/MLX graph in the app | Whether the port includes the speaker kernels; new runtime dependency |

Deliverables: a reference transcript set produced by the original NeMo model (run once off-line on a development machine, outputs stored as evidence, not shipped), then the candidate backend run on the same inputs.

Gate G0 (all required): per-speaker output matches NeMo reference within 2 points of cpWER on the frozen mixtures; speed at least 1.5x real time with two active speakers on an M-series 8 GB machine class or a documented higher floor; peak memory measured; licence read in full (NVIDIA Open Model License terms for the weights and any converted artifacts; redistribution and commercial-use implications recorded).

If G0 fails for all options, 1.3.0 ships without Multitalker, records the evidence, and the plan stops here. Everything below depends on G0.

## Phase 1: quality evidence on realistic audio (about 1 week, in parallel with late Phase 0)

The 1.1.0 diagnostic was two synthetic clips, which is too small to certify. Build a proper benchmark:

- Licensed natural data: AMI/ICSI-style meeting excerpts or LibriCSS if licences allow; otherwise FLEURS/LibriSpeech synthetic mixtures at controlled overlap ratios (0, 10, 20, 40 percent) and 2, 3 and 4 speakers. Record dataset revisions and hashes in `specs/research/1.3.0-overlap-fixtures.json`. Generated audio stays outside Git.
- Metrics: cpWER, speaker-attributed token timing error, count accuracy, partial-to-final stability, latency to first partial per speaker.
- Compare against the baseline of "Parakeet plus Sortformer labelling" so the product claim is a measured improvement, not a feature for its own sake.

Gate G1: cpWER at or below 25% for two speakers at 20 percent overlap and measured numbers published for 3 and 4 speakers. The advertised speaker limit is what was measured, not the model card's maximum.

## Phase 2: contracts and pipeline (about 1.5 weeks)

SCR-017 (new) specifies, before code:

1. `PartialSegment` gains an optional stable `streamID`/speaker slot and revision, so concurrent partials from different speakers never overwrite each other; single-stream engines keep today's behaviour.
2. Engine API for speaker-conditioned live recognition: input is audio plus a speaker-activity stream from the diarizer (Sortformer), output is per-speaker partials and finals with overlapping time ranges.
3. Speaker reassignment, stop/flush, cancellation, pause and resume semantics; what happens when Sortformer revises its labelling.
4. Persistence: finalized overlapping segments keep their own speaker and time ranges through Live, editor, library, search, translation and every export (SRT/VTT/TXT/JSON/DOCX etc.); overlapping segments in subtitle formats are emitted per speaker with correct, non-merged timing.
5. Residency: Multitalker plus Sortformer plus any translation engine run under the existing `ResidencyCoordinator`; admission refuses combinations that exceed the memory tier with a plain message.

Implementation: a `MultitalkerEngine` (id `multitalker.parakeet`) wrapping the chosen backend, a live pipeline that feeds Sortformer's activity into it, and a file path that diarizes first, then recognizes per speaker in windows with stitching. Catalog entry with pinned revision, hashes, size, `LicenseRef-NVIDIA-Open-Model-License` acknowledgement, `overlapRecognitionSpeakers` set to the measured limit, English only.

## Phase 3: product surfaces (about 1.5 weeks)

- Live: overlapping speakers show as separate lines/lanes with consistent speaker colours; per-speaker partials update independently; Live captions overlay shows the active speaker(s) without flicker.
- Editor: overlapping segments render and edit correctly (selection, split, merge, speaker reassignment, undo); timeline shows overlap.
- Translation: live and file translation keep per-speaker identity (one item per segment, no cross-speaker concatenation).
- Settings: Models browser lists Multitalker with the speaker limit, English-only note, memory need and licence; a clear "Overlapping speech" option in Live/Meetings that is off by default, explains the extra memory, and falls back to the normal engine when the model is missing or memory is short.
- Meetings and file queue: policy for when to use it (recording with 2+ detected speakers and overlap).
- Accessibility identifiers, VoiceOver labels per speaker lane, Reduce Motion for partial updates.

## Phase 4: verification and release (about 1 week)

- Unit tests per package with `swift test --no-parallel`; contract tests for two concurrent speakers, revision/finalization, cancellation and persistence round trips; env-gated real-model tests following the `NativeSpeechAcceptanceTests` pattern.
- UI tests: Live overlap fixture, editor overlap editing, Models browser entry and licence consent, including a packaged-app model install through the UI (a 1.1.0 gap that this release closes for the new entry).
- Real-hardware matrix: 8 GB and 16 GB at minimum, with peak memory and real-time factor recorded; sustained 30-minute live session with two speakers, microphone and system-audio sources (also closes the 1.1.0 capture smoke-test gap).
- Packaged smoke tests on the signed candidate; real Sparkle update 1.2.2 to 1.3.0 over local HTTPS with a temporary trusted certificate, then clean up.
- Docs: `CHANGELOG.md`, `specs/releases/1.3.0-notes.md`, website changelog entry (what is new, no limits section), Models section and fresh screenshots (light and dark) including an overlap Live capture, README bullet.
- Release per `CLAUDE.md`: bump `MARKETING_VERSION` 1.3.0 and `CURRENT_PROJECT_VERSION` 11, self-signed release script, appcast keeps older items, `verify-published-release.py v1.3.0`. Publishing and tag push need owner confirmation.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| No backend reproduces speaker conditioning | G0 is the first gate; fail early, ship 1.3.0 without it, keep evidence |
| Quality below the floor on natural audio | G1 is a hard gate; advertise only the measured speaker count; keep the feature behind an explicit opt-in |
| Memory: 0.6B model plus Sortformer plus translation on 8 GB | Residency coordinator admission, measured tiers, graceful fallback to the standard engine |
| Licence restricts redistribution or commercial use | Read in Phase 0; user-initiated download only, acknowledgement before download, notice shown in the app |
| Contract churn breaks existing engines | Additive optional fields only, compatibility tests for single-stream engines, no change to Apple/Whisper/Parakeet paths |
| Sortformer label flips produce scrambled lanes | Smoothing and reassignment rules specified in SCR-017 and tested with recorded activity traces |
| Compile differences between Xcode 26 and 27 | Hosted CI on the minimum toolchain at every checkpoint PR |

## Schedule and checkpoints

About 6 weeks, in checkpoint PRs (not one final dump): P0 evidence and decision, P1 benchmark and evidence, SCR-017 and contracts, engine and pipeline, product surfaces, verification and release. Push at gates, per the owner's preference.
